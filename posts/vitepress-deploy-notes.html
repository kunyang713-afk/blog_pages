VitePress 部署到 GitHub Pages 的踩坑记录 ​

把 VitePress 博客部署到 GitHub Pages 听起来很简单，实际坑不少。这篇记录我踩过的几个关键点，希望帮后来人少走弯路。

双仓库架构 ​

我的方案是双仓库：

  • 私有仓库 blog：存放源码，平时在这里写文章、改主题。
  • 公共仓库 blog_pages：只放构建产物，开启 GitHub Pages。

为什么分两个仓库？因为不想把源码（尤其是一些临时草稿、配置）暴露在公开仓库里。源码私有，产物公开，各司其职。

构建流程靠 GitHub Actions：push 到 blog 仓库 → 触发 workflow → npm run docs:build → 把 docs/.vitepress/dist 推送到 blog_pages 仓库的 gh-pages 分支。

最致命的坑：base 路径 ​

VitePress 默认部署在根路径 /，但 GitHub Pages 项目站点的 URL 是 https://用户名.github.io/blog_pages/，带了 /blog_pages/ 前缀。

如果不在 config.ts 里设置 base，所有静态资源（JS/CSS/图片）都会 404，页面白屏。

ts
export default defineConfig({
  base: '/blog_pages/',
  // ...
})

这一行救命。base 必须以 / 开头、以 / 结尾，和仓库名完全对应。

第二个坑：内部链接 ​

设置 base 后，Markdown 里的内部链接写法要注意：

  • 正确：[文章](/posts/hello-world) —— VitePress 会自动补 base 前缀
  • 正确：[文章](../posts/hello-world.md) —— 相对路径
  • 错误：写死 https://...github.io/blog_pages/posts/... —— 换域名就废

放心用 /posts/xxx 这种根路径写法，VitePress 内部会调用 withBase() 处理。

第三个坑：SSR 构建报错 ​

VitePress 构建时会做 SSR 预渲染。如果你的代码在模块顶层直接访问 window、document、localStorage，构建会直接挂掉：

ReferenceError: window is not defined

解决办法：

  1. 把浏览器 API 调用放进 onMounted 里（onMounted 只在客户端执行）。
  2. 或者用 <ClientOnly> 组件包裹只在浏览器渲染的内容。
  3. 顶部加 if (typeof window === 'undefined') return 守卫，保险起见。

我在写数字雨 Canvas 组件时就踩了这个坑，三种方法一起用才稳。

cleanUrls：好看的 URL ​

ts
export default defineConfig({
  cleanUrls: true
})

开启后 URL 是 /posts/hello-world 而不是 /posts/hello-world.html，更清爽。GitHub Pages 默认不支持，但 VitePress 构建时会生成对应的 .html 文件，配合 404.html 能正常工作。

GitHub Actions workflow ​

核心步骤：

yaml
- run: npm ci
- run: npm run docs:build
- name: Deploy
  uses: peaceiris/actions-gh-pages@v3
  with:
    deploy_key: ${{ secrets.DEPLOY_KEY }}
    external_repository: 用户名/blog_pages
    publish_branch: gh-pages
    publish_dir: ./docs/.vitepress/dist

注意 external_repository 指向公共仓库，用 deploy key 跨仓库推送。

最后 ​

部署看似繁琐，配好一次后基本不用管。每次 push 源码，几分钟后文章就上线了，这种自动化的小确幸，是写博客的动力之一。
